# 关系图校验（v1.0）

## 被校验的实际页面

“核心框架”板块的关系图只显示框架节点，以及端点均为框架的 `relationships` 边。`framework → decisionRule` 边虽然可以保留在数据里，但不会画在该图上。检查器 `scripts/verify_relations.py` 使用相同过滤条件，防止“门禁通过、图上没有线”。

“行动规则”板块的整体方法论图来自 `methodology.json`。其节点可通过 `methodIds` 关联多张行动规则卡片，详情展开后显示每张卡片的条件、行动、原因与出处。规则无需一条对应一个画布节点。

## 1.04 来源候选与独立查漏

新系统学习默认要求 `relation-ledger-v1`、`unit-record-v2` 和 `content-review-v3`。参见 [关系候选契约](relation-ledger.md)。`verify_relations.py --require-candidates` 检查候选与实际边双向映射；知识库已有新账本时会自动检查它。旧版按类型核对边的检查继续保留，但不能据此证明关系充分。

每个候选包括排除／合并项都须审核，每条实际边都须有来源候选。孤立框架记录实际搜索范围、候选处置及证据；没有候选可以如实说明，不必虚构候选或连线。整体方法论还要完成来源查漏及应用／论证情境检查。脚本不判断引文是否充分蕴含关系。

旧交付使用 `finalize.py --compatibility 1.03` 保留原门禁并明确缺少新版关系审核；带新单元／关系账本的数据不能退回旧契约。`--legacy-rule-ledger` 继续只用于更早的既有页面。

## 系统学习新页面

每个新系统学习 overview 都要先按 `action-rule-ledger.md` 逐单元记录并复查规则，再执行 `finalize.py`。它先验证规则账本，再检查框架可见关系图和整体方法论，最后在暂存目录完成覆盖、静态和 ZIP 检查。任何检查失败都不会留下同名交付半成品。

v2 规则账本中的 `relationReview` 分别复核框架图和整体方法论图。每种关系都写真实边 ID，或写出材料不支持该关系的具体原因。校验器核对记录与实际可见边是否一致；它不能单凭 JSON 证明语义正确，仍须回读原文。全是顺序主线时额外提示检查并行、条件分支、对比与反馈，但不强制添加任何一种。

- 两个以上框架、零条可见框架间关系：默认 ERROR。若材料确实不支持连接，规则账本用 `relationStatus: "unsupported"` 和具体 `relationReason` 明示，检查降为 WARNING。
- 有可见关系，但部分框架孤立：默认 ERROR。确实独立的框架在账本 `independentFrameworks` 中逐项写 ID 和理由。
- 全部关系为推断、推断比例过高或解释过短：WARNING，要求回看原文；不通过增加无来源边消除提示。
- 行动规则零条：只有规则账本中每个单元都完成复核，所有候选均有明确排除结果，且页面确实没有规则卡片时才通过。
- 每张行动规则卡片：必须有原始候选证据，且关联方法论节点或记录为独立规则。见账本校验器。

`--allow-empty` 只对没有新版账本的旧页面提供人工复核通道。新系统学习页不能用它跳过账本。旧页面重新交付使用 `finalize.py --legacy-rule-ledger`，交付清单不会声称完成规则账本检查。

脚本结构校验能证明“已记录的规则没有在卡片或图谱中丢失”。首次阅读是否漏提规则，仍要由逐单元保存和最后的专项原文复查控制。
